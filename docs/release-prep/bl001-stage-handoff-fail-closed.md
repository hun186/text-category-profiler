# BL-001：Stage 工作目錄交接的完成條件與安全限制

這次只針對傳統 `TCF_utils.TaskConnector.proc()` 的**階段交接路徑**，從可覆寫目的地的泛用 `RenameDir` 改為不可覆寫的搬移。其他呼叫舊版 `RenameDir` 的程式並未在此 PR 修改。Linux 使用 `renameat2(RENAME_NOREPLACE)`；Windows 使用原生 `os.rename`（目的地已存在會拒絕）；其他無安全替代 API 的 POSIX 平台會明確拒絕，避免將「先檢查再改名」誤當作原子保護。

## 問題

先前 `RenameDir` 遇到原生改名與備援複製都失敗時，可能只列印錯誤而返回；上層 `TaskConnector` 會當成成功並繼續下一階段。另一種情形是備援複製已產生目的地，但來源未刪除，形成**部分／不確定狀態**。不能把這種情況等同正常交接，亦不能因為是歷史 Ctrl+C 工作目錄就自動清理。

## 本次新契約

- 起始目錄名稱必須以精確的 `_is_running_<SrcTask>` 結尾，且確實存在；不得將父目錄中碰巧含這個片段的路徑當成工作目錄。
- 若 `_rdy_for_<DesTask>` 已存在，**直接拒絕**，不覆蓋／改名／刪除；即使其他程序在前置檢查之後才建立目的地，原生不可覆寫改名也應拒絕。Windows 另外拒絕 Junction／reparse 來源目錄。
- 經原有搬移函式返回後，只有**來源名稱已消失，且目的名稱確實成為資料夾**才視為交接成功；否則不是已完成。
- 同磁碟原生不可覆寫改名是安全交接基線；僅在 `EXDEV` 跨磁碟時，才使用 `copytree` 的**排他目的地建立**和 `rmtree` 備援。跨磁碟複製仍**不是原子交易**，部分複製失敗時不可假稱完成。
- 若來源仍在、目的地未建立，可沿原本三次上限重試；若來源和目的地皆在、或都不在，**立即停止**，不重試破壞性備援搬移，不自動清理任何一方。
- 達重試上限或結果不明時明確拋出 `HANDOFF_NOT_COMPLETE`，讓上層停止後續分類；不應只依日誌中的「嘗試改名」訊息認定交接完成。
- **已完成搬移後**的日誌寫入若失敗，只提示日誌失敗，不重做搬移，也不把交接成功偽裝成失敗。

## 驗證界線

`python -m unittest -v tests.test_bl001_task_connector_handoff` 的跨平台 CI，使用私有 TemporaryDirectory 模擬正常成功、靜默失敗、重試、部分複製、既有目的地、日誌寫入失敗、錯置名稱及連結來源。

**不操作任何正式 WorkPool**，不代表已在正式網路磁碟／Windows 多程序／所有交接呼叫者中驗證，也不代表 `_is_running_` 歷史目錄可清理、可恢復或有錯誤。這些工作目錄可能只是使用者 Ctrl+C 測試遺留資料，未經明確確認不應更動。
